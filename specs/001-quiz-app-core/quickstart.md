# Quickstart: Validating Quiz App Core End-to-End

This is a validation runbook, not a spec — it proves the feature works after implementation. Field/endpoint details live in `data-model.md` and `contracts/`; screen details live in `ui.md`.

## Prerequisites

- Docker and Docker Compose installed.
- A clean checkout of this repository (no prior `docker volume` state needed — the point of this guide is that it works from nothing).

## 1. Bring the app up (one command)

```
docker compose up --build
```

Expected: the `db` service (Postgres) becomes healthy; the `app` service runs `prisma migrate deploy`, seeds the database (only because it's currently empty — research.md), then starts Express serving both the API and the built React app on the port documented in `README.md`.

## 2. Log in as each seeded role

Using the demo usernames/passwords `README.md` documents (generated by the seed script, per FR-001a — this guide intentionally doesn't hardcode them here since they're README's responsibility to keep exact):

- **Student**: log in at `/login` (ui.md S1) with the seeded student credentials → should land on **My Quizzes** (S2) with at least one quiz under "Open".
- **Teacher**: log in with the seeded teacher credentials → should land on **My Quizzes** (T1) with at least one seeded quiz.
- **Admin**: log in with the seeded admin credentials → should land on **Dashboard** (A1) showing non-zero counts for classes/students/teachers/quizzes.

## 3. Student: take a quiz end to end (validates FR-001, 006–013, User Story 1)

1. From S2, open the seeded open quiz → **Quiz Intro** (S3) shows time limit, points, and the negative-marking sentence (FR-032).
2. Start it → **Taking Quiz** (S4): countdown ticking, one question per screen, autosave indicator toggling on each selection.
3. Refresh the browser mid-attempt → confirms resume with the same remaining time and answers intact (FR-008a, edge case in spec.md).
4. Submit → **Submit Confirmation** (S5) shows the correct unanswered count, then **Result** (S6) shows a score immediately, no per-question breakdown.
5. Try to open the same quiz again → blocked, shown the existing result instead of a new attempt (FR-007).

## 4. Teacher: build, publish, and check locking (validates FR-004, 005, 012, 023, 024, User Story 2)

1. From T1, create a new quiz (T2): title, classes, dates, time limit, negative marking.
2. Add questions (T3): confirm the UI rejects a question without exactly 4 options / exactly 1 correct answer.
3. Publish → confirm it's invisible to a student outside the assigned class or outside the date range, and visible/startable to one inside both.
4. Have a seeded student attempt it once, then return to T2/T3 as the teacher → confirm every field except the dates is now read-only (FR-024).

## 5. Import a quiz and student/teacher lists (validates FR-016–020a, FR-019a, User Story 3)

1. As admin, import the sample student spreadsheet (`server/prisma/sample-data/students.xlsx` or `.csv` — see README) via A5 → preview shows per-row status, confirm creates accounts and shows the printable credentials table.
2. Re-import the same file → previously created students are skipped as duplicates, not recreated (FR-020).
3. Attempt to import a CSV saved in a non-UTF-8 encoding → rejected before any row preview with "Save as CSV UTF-8 or upload XLSX" (FR-019a).
4. As a teacher, import the sample quiz spreadsheet (T4) → lands as a draft in the Questions Editor.

## 6. Results (validates FR-014, 015, 026, 027, User Story 4)

1. As the owning teacher, open Quiz Results (T5) for a quiz with several seeded attempts → per-student status/score, class average, per-question % correct all populated.
2. Export CSV → file downloads and matches the on-screen table.
3. As a different (non-owning) teacher, attempt to open the same quiz's results directly by ID → denied.
4. As admin, open the same quiz's results via A6/A7 → same screen, same data, no ownership restriction (FR-031c).

## 7. Admin: classes and users (validates FR-028–031d, User Story 5)

1. Create a class, then try to delete it while empty → succeeds. Move a seeded student into it, then try to delete it again → refused; archive instead → succeeds, and the moved student's past attempts and future quiz list reflect the change (FR-030).
2. Create a single user directly (A4) → behaves identically to an imported one (username scheme, printable credential).
3. Deactivate a user → login attempt for that user is denied; their historical data remains visible in results.

## 8. Arabic / bilingual UI (validates FR-022, FR-033–038)

1. Toggle language on the login screen → `dir="rtl"` applied, layout mirrors per `ui.md` §1.9.
2. Log in as a seeded Arabic-named student → name renders correctly (`dir="auto"`) in both UI languages.
3. Search for that student by name in the admin Users screen using a different alef variant / without diacritics than how the name is stored → still matches (FR-038).

## 9. Automated tests

```
npm test            # root — runs all workspaces
npm run lint         # root — must pass before every commit, per CLAUDE.md
```

Expected: server unit tests (`services/`) pass without a live server process; server integration tests (`routes/`, Supertest) run against the real test Postgres (constitution Principle II/VI — no DB mocking); client tests cover hooks with real logic (timer, autosave) per CLAUDE.md's testing rule. See `traceability.md` for the full planned test list mapped back to requirements.

## 10. Hardening spot-checks (validates constitution Principle II)

- Two browser tabs on the same quiz attempt: only one `Attempt` row is ever created (query the DB or watch for the 409 on the second tab's start call).
- Manually forge a client-side score or `is_correct` field in a submit request (e.g., via browser devtools): server ignores it entirely — score still comes from the stored answer key (FR-011).
- Submit a request a few seconds after the deadline: accepted within the 10-second grace window, rejected/auto-finalized beyond it (FR-008).
